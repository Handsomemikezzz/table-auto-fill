# 模型主导的简历填写：产品与实现设计

日期：2026-09-29  
状态：全量模型主导策略已按使用反馈调整为“规则优先、模型兜底”，见 [修复记录](2026-09-29-rules-first-autofill-fix.md)。原首版完成情况见 [实施记录](2026-09-29-model-led-autofill-implementation.md)。
补充资料现统一保存到个人资料，不再按网站记忆；见 [全局个人补充资料](2026-09-29-global-personal-fields.md)。

范围：简历资料、表单填写、异常处理和持续改进。  
取代：此前“规则先填写，未命中再调用模型”的目标流程。

## 1. 产品目标与明确取舍

用户打开招聘表单、选择本次资料、点击一次“填写当前页面”，系统理解整组问题，使用已有事实完成填写，最后只请用户处理真正需要人判断的少数事项。

所有自动填写的新语义绑定都必须经过模型决策。DOM 观察和执行器继续复用，规则作为可追踪的证据与约束输入。程序不因为某条正则命中就直接完成“字段含义→资料来源”的最终决策。用户明确选择一个值写入一个控件属于手动操作，无需模型重新推断，单独计为辅助完成。

初版保留一个主入口、一个任务面板和一个资料设置页。模型类型属于设置，不再成为三个功能按钮。自动填写以当前页面为范围；页面跳转后用户再次启动，首版不建设跨页面自主投递代理。

### 功能取舍

| 保留为核心 | 收到次级入口 | 移除或停止作为默认流程 |
| --- | --- | --- |
| 填写当前页面 | 只填某一区域 | 快速填充、AI 扫描、AI 框选三个并列模式 |
| 选择本次资料、查看来源 | 打开资料、复制单字段 | 每个失败项固定出现“填写并记住” |
| 停止、查看进度、处理待办 | 撤销本次可恢复的修改 | 每张卡片重复的大段识别纠错输入框 |
| 导入简历并确认资料更新 | 学习记录、备份同步 | 投递记录、岗位台账、状态统计 |
| 可选简历附件 | 模型连接与高级诊断 | 默认在网页各处插入“AI 生成”按钮 |

开放问答首版使用用户已有的自我评价、经历说明或已保存答案。自动编写新的个人经历不在主流程内；明确的文本整理能力可后续单独评估。

## 2. 一个统一的使用流程

### 2.1 准备

弹窗只展示当前资料、可选附件、一个主按钮“填写当前页面”，以及“打开资料”和设置入口。

资料来源与文件上传分开：

- “当前资料”决定本次使用的事实快照；所有字段都能追踪来源。
- “附件”只决定是否附加文件，默认不因为选择文件而暗中替换整套资料。
- 导入或重新解析简历生成更新草稿，由用户确认覆盖项；手工确认的事实优先，不静默用旧解析值覆盖。
- 缺失的学院、学习形式、日期精度保持缺失，资料加载器不补造默认事实。同一记录的事实矛盾时，只暂停依赖该记录的项目，请用户核对来源。
- 默认只呈现通用资料，多份岗位资料作为可选能力展开，不要求新用户理解“解析快照”等内部术语。

### 2.2 执行

点击后显示轻量的页面任务面板，阶段为“理解表单 → 匹配资料 → 填写并检查”。字段清单尚未确定时不显示虚构百分比；执行后显示已验证数量与待处理数量。

按逻辑模块决策，按依赖逐项执行。已确定的模块可以先完成，其他模块继续理解。停止始终可用，停止后不再上传附件、新增经历或开始新的填写动作。

现有用户输入默认保留。模型可指出与资料不一致的项目，但覆盖需要用户针对该字段明确选择。撤销只处理仍能证明属于本次填写的值，保护用户后来修改的内容。

### 2.3 结束

成功后任务面板收起为简洁摘要。有问题时显示“已填写 18 项，3 项需处理”这类真实计数，用户进入同一个待处理队列。

待处理列表显示字段名、所属经历、一个简短原因；默认展开当前一项。处理后进入下一项。用户跳过的项目单列，不计入自动完成数。日期范围按逻辑组检查，不让其中一个端点成功掩盖另一个端点错误。

## 3. 决策架构

    页面观察 ─┐
    本次资料 ─┤
    字段定义 ─┼→ 模型决策 → 本地约束检查 → 执行计划 → 控件操作 → 独立验证
    已确认纠错┤       ↑                                        │
    历史证据 ─┘       └──── 新选项、联动变化、失败证据 ───────────┘

### 3.1 页面观察层

复用当前 DOM/ARIA、控件分组、选项与位置采集能力，产生页面事实：

- 稳定字段 ID、所属 frame、逻辑容器、相对位置及节点版本。
- 标签、说明、必填、当前值、类型和控件可执行能力。
- 当前真实选项、选项身份及“未读取/部分读取/完整”的状态。
- 相邻字段、模块标题、可能的记录组和依赖关系。

观察层可以提议“这两个输入框共享起止时间标签”，但不直接决定它们来自哪条教育经历。候选生成必须保留未知字段；规则未命中不是删除候选的理由。

### 3.2 模型决策层

每次新填写会话，所有拟填写的逻辑字段都进入模型决策或复核。模型可按模块批量回答多个有类型的问题：

1. 这个字段的业务含义是什么？属于谁的信息？
2. 这个模块对应哪一条已有记录？
3. 应使用哪个已存在的事实？
4. 目标选项是哪一个？还是需要先展开、搜索更多选项？
5. 下一步是执行、读取更多信息、询问用户，还是停止该字段？

模型看到规则给出的候选解释，也能选择其他已定义字段、已有补充信息或“新字段/无法确定”。已知标签的候选不能只有一个，否则模型只是为规则盖章。

输出只引用受约束的身份和操作：

    FieldDecision
      fieldId / snapshotVersion
      meaningId / subject
      recordId / factId
      targetOptionIds（可选）
      dependencyIds / expectedResult
      nextAction: write | select | readOptions | requestFact | requestMeaning | manual
      evidenceIds / uncertaintyReason
      modelId / registryVersion / profileVersion

实际值由程序通过 factId 读取，禁止模型生成不存在的日期、学校、姓名等事实。模型不生成 CSS 选择器、任意 JavaScript 或后端提交请求。

### 3.3 Laya 与 LLM 的关系

统一 DecisionProvider 协议，产品入口与模型供应方分离：

- Laya 用于给定候选中的含义、记录、选项和下一动作决策，中文任务评估 multilingual。
- LLM 用于复杂关系、开放的新字段理解以及难以构造明确候选的情况。可从一开始就承担某个模块的决策，不必等规则失败。
- 模型路由依据任务与已配置能力；两者都处于正常决策路径。
- 首次实现可先用已有 LLM 接口贯通所有字段的决策协议，再把 Laya 接入同一协议并用相同样本比较。首版不绑定某个模型才能使用。

如果只配置本地模型，不因一次不确定就静默把资料发到云端。云端升级需用户在设置中明确启用。模型不可用时显示“暂时无法连接填写服务”，保留手动资料助手，不暗中恢复规则自动填写。

### 3.4 规则的角色

| 规则类型 | 作用 | 不能做什么 |
| --- | --- | --- |
| 字段语义定义、别名、示例 | 帮助模型形成和比较候选 | 不能命中关键词后绕过模型绑定资料 |
| 用户确认的站点含义 | 作为高优先级、有限范围的上下文 | 不能覆盖另一用户或其他网站的资料 |
| 控件能力与格式规则 | 指定可执行操作和无损格式转换 | 不能猜 0/1 编码或补造日期 |
| 系统硬约束 | 检查资料存在、目标身份、记录一致性、数据权限 | 不承担开放语义的同义词裁决 |

模型通过真实选项判断出一种新的等价表达后，不能又被旧字符串别名表一律否决。仍需验证选项真实存在、属于当前控件、可选，且事实、主体、记录与日期精度没有改变。

## 4. 提效方式

效率来自减少重复信息和无效调用：

- 一次处理一个逻辑模块，一批返回多个字段决策，避免每个输入框重复发送整份简历。
- 先提取局部上下文，再检索候选事实和相关字段定义；不发送整页 HTML。
- 候选分层：先确定模块/主体，再选记录和字段；保留“其他/无法确定”出口。
- 缓存资料规范化、字段定义检索、页面结构与候选选项；本地模型可预热。
- 同一会话内已验证且未变化的字段不重复决策。跨会话的旧决策只作为模型复核证据；首版不使用“规则/缓存命中即写入”的旁路。
- 资料、目标控件、上游依赖、选项或规则版本变化后，只让受影响的字段重新决策。
- 页面操作串行，独立模块的模型计算可以并行；取消优先。

实际延迟、内存与请求成本以本机和招聘样本实测为准，不承诺宣传页中的推理耗时。显示阶段反馈，避免用户因没有反馈重复点击。

## 5. 重新设计截图中的失败处理

原有卡片把缺资料、理解错误、执行失败与验证失败都压成“输入一个值、填写并记住”，让用户承担了本应由系统定位的问题。

新的待处理项必须基于失败类别生成交互：

| 状态 | 用户看到的内容 | 主要动作 | 数据处理 |
| --- | --- | --- | --- |
| 已显示值，提交状态未确认 | 展示资料值与网页读回值；“日期已显示，尚未确认保留” | 重新检查 | 先读回，不立即重复写入或修改资料 |
| 答案明确，控件未选中 | “学校需要在网页下拉中选中”及已有学校名 | 在网页中选择 | 定位控件，手动完成后检查 |
| 资料不足 | “网站要求具体日期，资料只有年月” | 补充日期 | 只向用户补充缺少的精度；不默认 1 日 |
| 含义不确定 | 问题原文与 2–3 个候选解释 | 确认含义 | 更正该字段含义，重新生成计划 |
| 经历不确定 | 展示候选记录的学校、学历、时间 | 选择对应经历 | 同一逻辑组整体重新绑定 |
| 页面已变化 | “字段已更新，正在重新识别” | 通常无需用户操作 | 重新读取该组，模型复核新目标 |
| 全部候选都不适用 | 展示现有资料及实际网站选项 | 选择/跳过 | 不用近似匹配强选第一个 |

共同的次级动作只有“本次跳过”和折叠的“更多”。“查看来源/更正理解/诊断信息”按需展开。没有必要时，不出现自由文本纠错输入框。

### 对截图两项的具体设计

- 毕业时间：首先核对 2022.6.1 与网页读回值是否是同一天，及是否稳定保留。若值一致但状态未确认，显示“重新检查”；若缺真实日期精度，则请求补充。不能把错误统一归因于用户的值。
- 学校：已有“安徽大学”这个答案，先由模型选择读取更多候选或更换已支持的操作。仍无法定位真实列表时，定位原控件让用户选择；不再要求重新输入学校名。

失败回到模型时必须附带新证据，例如选项集合、当前值、页面错误和已尝试动作。相同状态下不重复询问或执行相同动作。初始预算建议每字段最多两次有差异的恢复计划；超过预算即明确交接，不让单字段卡住整页。

## 6. “记住”拆成三件事

### 6.1 保存资料事实

只在用户确实补充或修改事实时出现，例如最早到岗日期。默认本次使用，用户可以勾选“保存到我的资料，下次可用”。应显示所属资料版本，避免误改另一份简历。

即使网页控件填写失败，用户明确要求保存的真实资料也应可以保存；“保存成功”和“网页填写成功”分别反馈。时间敏感信息带更新时间，过期时重新确认。

### 6.2 记住字段含义或资料绑定

用户纠正“这是紧急联系人的电话”后，生成结构化记录：该网站、该表单结构、该字段应引用紧急联系人信息。显示简短提示“已用于本网站，下次可修改或撤销”。

只有用户明确确认过的语义纠错才成为高优先级规则。单凭网站接受了一个值，不能证明字段语义正确，更不能自动推广为全局规则。

### 6.3 记录控件操作经验

验证成功的操作、格式转换和组件特征可作为执行证据保存。它描述“这个控件怎样操作”，不把网站的数字编码写成个人资料。

规则和经验均带作用范围、版本、来源和失效条件，下一次由模型参考或复核。网站结构改变、选项改变、资料改变时失效或降为待验证。用户可在设置中查看、禁用和删除。

## 7. 新字段如何加入系统

新字段不应要求同时修改枚举、switch、提示词和校验器。建立一份可扩展的字段定义表，驱动候选生成、资料表单和模型约束。

    FieldDefinition
      id: availability.earliestStartDate
      label: 最早到岗日期
      subject: self
      valueType: date
      precision: day
      sourceCollection: additionalFacts
      aliases: [可到岗时间, 到岗日期, earliest start date]
      positiveExamples / negativeExamples
      allowedTransformations: [date-format]
      scope / version / provenance

新增流程：

1. 发现控件但现有定义不匹配，模型返回“已有补充信息”或“新字段候选”，而不是让控件消失。
2. 如果已有事实能回答，绑定现有 factId；不要重复建资料。
3. 否则以自然语言向用户提问，确认含义、主体与答案，并选择是否保存。
4. 生成用户范围的字段定义/纠错记录，模型在下一次决策时读取。
5. 开发侧收到用户主动导出的脱敏诊断后，整理正反例，评审是否进入通用字段定义表。
6. 增加回归样例，验证通过后随版本发布；如果是新控件交互方式，再增加控件适配器。

“新语义字段”“缺少一个事实”“新的网站写法”“新控件交互”是四类不同变更。文字规则可以改善前三者的决策；不会凭空增加一种尚未实现的控件操作。

不自动上传个人表单或启动在线训练。第一阶段的迭代依靠字段定义、检索到的纠错、版本化约束和回归样本；Laya 微调属于有足够标注数据后的独立工作。

## 8. 接口与最小模块划分

保留现有观察层与执行器，新增或调整四个边界：

- ProfileSnapshot：唯一、可解释的本次事实集合，带来源和版本。
- FieldRegistry：字段定义、示例和用户修正；规则更新在这里集中管理。
- DecisionProvider：LLM 或 Laya 都返回同一类受约束决策。
- FillSessionController：驱动观察、决策、执行、验证、局部重规划与待处理队列。

控制器不自行用正则确定资料绑定；执行器不选择哪条教育经历；验证器不负责把候选表达全部压回旧别名字典。业务语义正确性与页面状态正确性分开记录。

每个结果保留 decisionId、字段 ID、主体、事实/记录 ID、模型与规则版本、执行方式、失败阶段和验证证据。默认不记录完整简历、验证码或完整网页 HTML；详细诊断由用户主动导出。

## 9. 验收与迭代顺序

### 第一阶段：主路径改造

建立唯一资料快照与 DecisionProvider，所有目标字段经过模型，接通通用执行与验证。用测试防止“规则命中后直接写入”的旧路径重新出现。

### 第二阶段：精简交互

合并填写入口，落地单个任务面板、分类待处理项和来源查看。截图中的两种失败分别用重查/定位处理，新增资料只在缺事实时出现。

### 第三阶段：字段定义与纠错

新增字段通过定义表和 additionalFacts 扩展。完成限定范围的纠错保存、撤销、版本失效与回归样例生成。

### 第四阶段：Laya 与效率验证

在同一协议下比较 LLM、Laya、多模型路由。测中文字段含义、记录绑定、真实选项选择、置信度校准、延迟和内存。模型的默认选择由结果决定。

每阶段使用同一批人工标注的基准，并增加未参与开发的招聘系统作为留出样本。漏识别、不支持、执行失败和无法验证均计未完成；人工操作单列。建议目标为资料充分字段的自动完成率至少 80%，自动写入项准确率至少 99%，关键身份与经历归属误填阻止发布。目标尚未实测。

另测首次使用到开始填写的操作数、每次填写要求用户作答次数、重复纠正率、规则更新后的回归率，以及最慢模块的处理时间。减少用户操作与减少误填必须同时成立。

## 10. 本轮交付与待决策项

本轮只有设计文档与交互草案，不改变现有插件行为，也不启动 Laya。

建议默认采用“一个任务面板 + 待处理队列”。“贴近字段的小提示”作为较轻的替代交互供对比，不另增加一个产品模式。两种界面共用同一模型主导的会话流程。
